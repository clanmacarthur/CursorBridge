## 3. Why v9.21 failed

### 3.1 It used the image library as decoration

The build selected images from `/mg_crops/` and appended them beneath generic text. It did not reproduce the original drawing logic or the customer decision path.

### 3.2 It stretched small crops

Several important accepted panels are only 190–632 pixels wide. They were displayed at full content width, causing blur.

Examples:

- `M_school_community.png` — 190 × 220
- `L_product_propagation_material.png` — 246 × 220
- `A_what_comes_in_box.png` — 340 × 270
- `B_box_opens_cross_deployment.png` — 363 × 279

### 3.3 Cropping separated labels from their meaning

The source boards were composed spatially. Tight crops removed neighbouring labels, arrows and contextual relationships. Enlarging the crop did not restore the missing information.

### 3.4 It omitted the actual click tree

The pitchdeck displayed static diagrams but did not show the user choosing:

- the result they want;
- the space they have;
- the application route;
- existing and wanted species;
- exact plants or functional alternatives;
- module format;
- permanence and location;
- monitoring;
- cost and maintenance;
- the generated output.

### 3.5 It mixed three different subjects

The section combined:

1. customer selection;
2. physical-system architecture;
3. application examples.

These require separate surfaces.

### 3.6 It did not map illustrations to the correct audience

School, corporate, household, restoration and public-space examples were not separated. Generic images were shown without the audience-specific logic already present in the source library.

### 3.7 It added generic captions

Some captions were newly written summaries rather than exact source labels. For this section, that introduces avoidable interpretation and must stop.

## 4. Correct reconstruction

The Modular Gardens section should contain three distinct visual systems.

# A. Customer Experience / Click Tree

This is the interactive journey that shows how someone creates a Garden-in-a-Box or larger Modular Garden.

## Entry route

The first choice is not always a product.

- By need
- By space
- For schools
- For workplaces / corporate sites
- For land restoration
- I already have equipment

- I want monitoring or irrigation
- I want to share or request plants

## 5. Source-faithful visual rules

1. Use exact source assets.
2. Use exact source labels.
3. Do not write new technical claims into captions.
4. State when an image is an accepted baseline, working concept, mock customer view or future route.
5. Never enlarge low-resolution crops until they become visibly blurry.
6. Reproduce labels as HTML beside the original image where the source text is too small.
7. Do not merge unrelated images into a new collage.
8. Do not use generated images as evidence of a settled physical design.
9. Keep corporate, school, household, public and restoration examples in their correct routes.
10. Link every displayed drawing to the source asset register.

## 7. Decision required before implementation

The source library contains two useful customer views:

1. **Simple customer route:** choose a result → choose a starter → add extras → review.
2. **Full builder route:** plot and permissions → assets and ecology → outcomes → species/guilds → module → monitoring → generated proposal.

Recommended structure:

- **Basic:** the simple customer route, with full human explanation.
- **Intermediate:** the complete Plot Studio working route.
- **Advanced:** the generator contracts, botanical prerequisites, permissions, state model, dashboard blueprint and system adapters.

This preserves both source-backed routes without treating either as the whole system.
