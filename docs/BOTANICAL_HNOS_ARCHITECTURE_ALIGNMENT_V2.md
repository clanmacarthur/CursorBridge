# Botanical HNOS Architecture Alignment V2

Last updated: 2026-03-31

## Position

The botanical system should remain standalone-capable while staying HNOS-compatible.

## Required Alignment

- stable IDs across botanical, zone, product, and overlay layers
- explicit separation between identity, operational, product, protocol, and governance layers
- explicit separation between companion logic and symbiosis logic
- versionable and publishable records
- import/export safe contracts for cross-repo work

## Required HNOS-Aware Behaviors

- branch-aware expansion
- relation-safe data sync
- staged publication workflows
- attribution and governance handling
- support for future module/add-on logic without flattening botanical truth
- universal layering across ecological, module, restoration, and planning contexts
- two-way product navigation:
  - product -> matching botanical entries
  - botanical entry -> valid product paths

## Engine Rule

Compatibility logic should stay hybrid:

- trait-based scoring
- curated compatibility rules
- user override layer
- policy filtering last

## Constraint

Do not tightly couple the app runtime to one hardcoded botanical branch. UK and Brazil must remain parallel branches within one shared system.
